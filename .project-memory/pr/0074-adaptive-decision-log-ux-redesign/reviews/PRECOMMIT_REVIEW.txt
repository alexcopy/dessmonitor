VERDICT: APPROVED

B1 STATUS: resolved

The revised grouping key compares event type, worker_id, and the complete canonical payload. Battery-response,
baseline, and cutover events are never grouped. Confirmation entries are described from their from/to payload,
so count decreases are labelled resets and pending-candidate changes remain visible. Distinct state or stability
transitions have different payloads and therefore remain separate.

State revision is metadata for the journal state as a whole, not the transition identity. In
adaptive_journal_v2.py, _derive_events() emits CONFIRMATION_CHANGED whenever pending or stable_count changes;
its payload records both from/to values. A repeated confirmation transition after a reset must have an intervening
reset event, so adjacent identical transitions cannot conceal that reset. Other derived state transitions similarly
carry changed before/after values, and their intermediate reversal is an intervening event. Revisions can also
advance for evidence fingerprint, contrast, or algorithm state while no material outcome event is emitted; including
revision in the key would prevent condensing otherwise identical transitions without adding transition detail.
No counterexample was found in the actual event derivation schema for adjacent, exactly payload-identical events.
This conclusion depends on the current _derive_events() contract and should be revisited if new event types omit
their before/after state from payloads.

The API query in app/web_queries.py returns events ordered by event_time DESC, event_id DESC. groupEvents() preserves
that order; the first five groups are rendered. Full returned event objects, including event_id, state_revision,
worker_id, timestamps and payload, remain available in the raw-event disclosure. No event record is removed from
the API result or raw history.

B2 STATUS: resolved

The focused UI suite now covers confirmed HYPOTHETICAL_RAISE and HYPOTHETICAL_LOWER, missing candidate voltage and
missing/partial confirmation fields, pending candidate under HOLD, confirmed versus unconfirmed stability,
confirmation progress, and verified versus unverified current settings. Tests assert Back to Battery is displayed,
recorded candidate voltage is shown without invention, only stability CONFIRMED is described as confirmed, and
all proposal text remains explicitly hypothetical and non-actionable without implying permission to write settings.
The entry shape matches online_output_learning.py: decision is the candidate code, threshold is the 'battery' key,
proposed_voltage/candidate_voltage carry the candidate, stability is CONFIRMED on confirmation,
actionability is NON_ACTIONABLE, and confirmation_progress carries confirmed/required counts.
