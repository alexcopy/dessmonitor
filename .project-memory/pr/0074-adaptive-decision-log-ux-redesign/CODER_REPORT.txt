FINDING B1 — EVENT GROUPING COULD HIDE MEANINGFUL TRANSITIONS

Cause: groupEvents() merged every adjacent CONFIRMATION_CHANGED event by type alone, showing only the newest
summary with a count, and merged other events by type + label + summary text; BATTERY_RESPONSE_CHANGED always
had the same text, so distinct occurrences were merged.

Resolution:
1. Explicit equivalence rule (equivalenceKey/canonical): two ADJACENT events are merged only if event_type,
   worker_id and the complete payload are identical, compared as canonical JSON with sorted keys.
   event_time, event_id and state_revision are treated as per-occurrence identity, not content. Any payload
   difference keeps events separate. Merged entries say "Identical event recorded N times since <time>".
2. Never merged: BATTERY_RESPONSE_CHANGED (its payload cannot establish that two occurrences are the same
   state change), JOURNAL_V2_CUTOVER, BASELINE_RECORDED.
3. CONFIRMATION_CHANGED is described from its payload: "Confirmation reset" when stable_count decreases
   (warn tone), "Pending candidate changed" when only the pending candidate changes, otherwise "Confirmation
   progress changed"; the text states the count transition and the pending candidate
   (HYPOTHETICAL_RAISE:26.5 -> "hypothetical raise to 26.5 V"; unknown formats shown verbatim; missing
   counts "not recorded", no longer defaulted to 0).
4. BATTERY_RESPONSE_CHANGED shows its interpretation when it is not the default
   EMPIRICAL_RESPONSE_CHANGED_CAUSE_UNKNOWN.
5. The type-based "minor event" filter was removed. It could drop recent confirmation changes from the
   default view in favour of older events, which conflicts with "never hide a change in confirmation count,
   pending candidate or stability". The default timeline now shows the newest five entries in API order
   (newest first) and states how many other events are in the full history. Consequence: during bursts of
   confirmation or battery-response activity, older worker/evidence events move into the full history
   instead of being prioritised; the current worker state is still shown by the primary panel's worker
   status and attention line.
6. Full event history unchanged: every original event object (verbatim JSON), its full timestamp and its
   payload remain available, uncondensed.

FINDING B2 — NO REGRESSION COVERAGE FOR CONFIRMED HYPOTHETICAL_RAISE / HYPOTHETICAL_LOWER

Resolution: dedicated tests using the entry schema built by app/control/online_output_learning.py for a
confirmed candidate (decision HYPOTHETICAL_RAISE/LOWER, threshold 'battery', proposed_voltage =
candidate_voltage, stability CONFIRMED, actionability NON_ACTIONABLE, confirmation_progress
{confirmed: 2, required: 2}, cooldown 3600 s, current_settings provenance unknown).

Directly related defects found while writing these tests and fixed (presentation only, no decision logic):
a. Real entries store threshold as the key 'battery'; the candidate line and the "Hypothetical proposal"
   row printed "battery 26.5 V". They now show the monitored threshold label ("Back to Battery") via
   thresholdName(); HYPOTHESIS_CREATED event text likewise.
b. The proposal line now distinguishes a confirmed decision ("Confirmed hypothetical raise: Back to Battery
   26.5 V — non-actionable; confirmation 2 of 2.") from a pending candidate ("Hypothetical candidate: …");
   "Confirmed" is used only when stability is CONFIRMED.
c. A HYPOTHETICAL_RAISE/LOWER decision with no voltage previously showed no candidate line and the row
   "No proposal"; it now says "(voltage not recorded)" / "Voltage not recorded (hypothetical;
   non-actionable)". Missing or partial confirmation_progress is reported as "confirmation not recorded".
d. The consequence for a hypothetical decision now reads "Hypothetical proposal for review only —
   non-actionable. This system does not write inverter settings." It describes the system, not the
   hardware state.
