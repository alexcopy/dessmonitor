TITLE
PR 0034j — Carry Sensor Telemetry Through the Complete Runtime Snapshot

CONTEXT
Production sensors now report temperature around 20.9°C through the ML and
inverter-summary compatibility path (Path B: shared_state["water_temp"]).
The authenticated dashboard at GET /control/state still displays "No sensors
available" because the typed snapshot pipeline (Path A) drops sensors before
serialization.

This PR does NOT change Tuya polling behavior, status routing, or telemetry
collection. It fixes only the snapshot contract — the typed data path from
TelemetryRegistry through ControlStateSnapshot to the dashboard.

PRODUCTION EVIDENCE
- Path B: shared_state["water_temp"] ≈ 20.9 → MLDataCollector and inverter
  summary logs show correct temperature.
- Path A: TelemetryRegistry populated → runtime_state["sensors"] populated →

  code reads runtime_state["sensors"].
- Dashboard: snapshot.sensors is undefined → renderSensors() shows empty row.
- Load descriptions: _device_to_load_dict creates "description" key; _parse_loads
  ignores it when converting dict to RuntimeLoadState.

DOMAIN TYPES

SensorReadSnapshot
Module: app/control/control_state_snapshot.py (alongside LoadControlSnapshot)

Rationale: A new sensor type is required because SensorTelemetryReading
lives in app/devices/sensor_telemetry.py (domain model) and contains an
observed_at datetime (internal type). At the /control/state web boundary,
observed_at must be an ISO string or None. The new type also adds device_type
(canonical string) and drops internal fields never exposed through the API.
This avoids coupling the control snapshot layer to the device telemetry model.

Required safe fields:
  sensor_id: str = ""
  display_name: str = ""
  description: str = ""
  device_type: str = ""
  metric: str = ""
  value: float | None = None
  unit: str = "celsius"
  observed_at: str | None = None
  source: str = ""
  freshness: str = ""
  status: str = ""
  communication_status: str = ""

Contracts:
- value is float or null.
- observed_at is ISO string or null at the web boundary.
- description defaults to "".
- device_type is canonical and controlled (normalized by normalize_device_type).
- No Tuya parent ID.
- No DP property code.
- No raw status payload.
- No credentials.
- No runtime exception text.
- Frozen dataclass (mutable for FastAPI serialization? Confirm — existing
  LoadControlSnapshot is frozen and FastAPI serializes it correctly via the
  router returning WebUiControlStateResponse which contains it as a nested
  dataclass. FastAPI + Pydantic v2 auto-serializes frozen dataclasses.)

SENSOR SNAPSHOT CONTRACT
Layer            | Representation          | observed_at type
TelemetryRegistry| SensorTelemetryReading  | datetime | None
get_all_readings_dict | dict             | ISO string | None
runtime_state["sensors"] | list[dict]  | ISO string | None
_parse_sensors    | SensorReadSnapshot     | str | None
ControlStateSnapshot | SensorReadSnapshot  | str | None
WebUiControlStateResponse | nested        | str | None
GET /control/state JSON | "sensors" array | ISO string | null
dashboard.js      | snapshot.sensors       | string | null → rendered as timestamp

LoadCandidate (app/control/policy_models.py):
No changes. LoadCandidate is the control engine's view of loads and should
not own display-only metadata. The new fields stop at RuntimeLoadState and
are mapped directly to LoadControlSnapshot.

LoadControlSnapshot (app/control/control_state_snapshot.py):
Add these fields:
  description: str = ""
  device_type: str = ""
  mapping_status: str | None = None
  startup_reset_result: str | None = None
  enabled: bool = True
  communication_status: str | None = None

_convert_load() must read these from LoadCandidate (or RuntimeLoadState via
the adapter) and pass them to LoadControlSnapshot.

Note: Since LoadCandidate does not own these fields, the adapter
(build_runtime_control_snapshot / _to_load_candidate) must carry them
separately. The cleanest approach: add a load_metadata mapping in the
adapter input or pass the extra fields through a separate typed list.
Preferred: extend RuntimeLoadState so the fields are typed all the way
through, then map into LoadControlSnapshot while LoadCandidate stays clean.

Implementation approach in build_runtime_control_snapshot:
- Keep LoadCandidate as is (control-only).
- In _convert_load → LoadControlSnapshot, use a parallel metadata lookup
  keyed by load_id, or pass the additional fields through the adapter input.
- Simplest: add a `load_metadata: dict[str, Any]` to
  RuntimeControlSnapshotAdapterInput, or extend RuntimeLoadState and have
  _to_load_candidate strip the display-only fields before creating LoadCandidate.
- Decision: extend RuntimeLoadState with all fields, then have
  _to_load_candidate ignore them, and have build_control_state_snapshot
  pass them directly to _convert_load via the snapshot input.

SECURITY BOUNDARIES
- SensorReadSnapshot exposes only safe fields: sensor_id, display_name,
  description, device_type, metric, value, unit, observed_at (ISO string),
  source (controlled), freshness, status, communication_status.
- NEVER exposed: tuya_device_id, control_key, state_key, property codes
  (temp_current), raw status lists, credentials, tokens, signed URLs,
  exceptions, operational configuration.
- Description and display_name are operator-controlled text. They are rendered
  via textContent (not innerHTML) in dashboard.js — already safe.
- _parse_sensors and _parse_loads use try/except with safe defaults for
  all fields. No exception text leaks.
- No new write paths. No new endpoints. No new public routes.

REGRESSION RISKS
- Adding sensor field to frozen dataclasses may break callers that rely on
  positional argument unpacking. Mitigation: all new fields have defaults and
  are keyword-only at the boundary; existing callers using keyword arguments
  are unaffected.
- Adding fields to RuntimeLoadState may break existing tuple of field references.
  Mitigation: RuntimeLoadState uses keyword construction in _parse_loads;
  existing callers constructing RuntimeLoadState directly with positional args
  are rare. Audit before implementation.
- FastAPI serialization of new nested dataclass (SensorReadSnapshot) has been
  tested previously with LoadControlSnapshot and works. No risk.
- Empty-sensor edge cases: empty tuple → dashboard shows "No sensors available"
  (existing behavior). One missing field → safe default. All fails covered.
