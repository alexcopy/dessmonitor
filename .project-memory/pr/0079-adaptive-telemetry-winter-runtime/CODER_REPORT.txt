  PRECISE FIX (app/ml/timescale_data_collector.py)
    1. Loop-boundary isolation. timescale_collection_loop() now guards each
       activity separately with `except Exception` (CancelledError is a
       BaseException and is never caught there):

         - persist_pending_events()  -> flush fault (raised, or a failed write
                                        reported via persist_failures)

       A failing collection never stops the event flush (and vice versa).
    2. After a fault: _after_fault() sets persistence_status "degraded" and
       probes the pool (connection_healthy(): SELECT 1, 10 s timeout). A broken
       pool is discarded by reset_connection(): terminate() at once (only this
       loop uses the pool and it resets between operations; a graceful close()
       was observed to stall up to 10 s on a connection asyncpg left in an
       InternalClientError state), _is_initialized=False. The loop then
       re-initialises with back-off; queued events and their stable persistence
       keys are untouched.
    3. Bounded back-off per activity (_FaultBackoff): 5, 10, 20, 40, 80, 160,
       300, 300 ... s (LOOP_RETRY_INITIAL/MAX_SECONDS). Collection retry waits
       for retry_at; the flush keeps its existing 30 s floor
       (PERSIST_RETRY_SECONDS); after any fault the loop sleeps at least
       min(flush interval, 5 s). No zero-length waits after a failure.
    4. Bounded logging: one WARNING with traceback at the start of a fault
       streak, then at most one summary per LOOP_FAULT_LOG_INTERVAL_SECONDS
       (300 s) with the consecutive and suppressed counts; one INFO on
       recovery. persist_pending_events() now logs each failed attempt at DEBUG
       only (it previously warned every 30 s indefinitely) and records
       last_persist_outcome / last_persist_error for the loop.
    5. Recovery: once the database is back, initialize() succeeds, collection
       resumes and the flush drains the retained queue without an application
       restart. The flush streak resets only after an actual verified write or
       an empty queue ("written"/"idle"), never during the writer's own back-off.
    6. Shutdown/cancellation: every wait is _wait_for_stop(stop_event, ...), so
       stop is immediate. `except asyncio.CancelledError` now re-raises (it
       previously swallowed cancellation); close() still runs in finally.
    7. Unrecoverable exit: if anything escapes the guarded calls (an
       Exception outside them, or a non-Exception error), finally detaches the
       writer: persistence_status "disabled", queued events counted in
       queue_drops, nothing further is queued. A normal stop or cancellation
       leaves "unavailable". Unrecoverable configuration (no DATABASE_URL /
       asyncpg) still detaches as before.

       exact-set acknowledgement, bounded queue (256) with explicit drop

  BLOCKER 1 — false persistence acknowledgement (FIXED)
    Root cause: persist_pending_events() used INSERT ... ON CONFLICT DO NOTHING,
    ignored the command tag and acknowledged the whole batch; the persistence
    time (PK) was regenerated on every retry, so a lost COMMIT acknowledgement
    could also produce duplicates.
    Changes:
    - TelemetryEvent.event_id: uuid4 hex assigned at enqueue; stored in the event
      metadata JSONB (one extra bounded key; no schema change). Stable identity
      across retries, processes and restarts.
    - Stable persistence key: the power_mode_events/inverter_metrics time is
      assigned once per event on its first write attempt (_event_key) and reused
      on every retry. Keys are dropped on acknowledgement and pruned to events
      still queued, so the map is bounded by the queue size.
    - inserted_rows(): parses the PostgreSQL command tag. Only "INSERT 0 1"
      counts as stored; "INSERT 0 0" is a conflict; anything else (None,
      "UPDATE 1", "INSERT 0 2", malformed) is unverified and raises.
    - _write_event(): each event runs in a savepoint inside the batch transaction.
        INSERT power_mode_events = 1 row -> (observed changes) INSERT
          inverter_metrics must also be 1 row; 0 rows there means the key is held
          by another metrics row -> savepoint rolled back, event re-keyed.
        INSERT power_mode_events = 0 rows -> PK lookup
          SELECT metadata->>'event_id' FROM power_mode_events WHERE time = $1.
          Equal to this event's id -> "existing": the row (and its metrics row,
          committed in the same savepoint) was stored by an earlier attempt whose
          acknowledgement was lost; handled without a duplicate.
          Different/absent id (foreign or legacy row) -> re-key and retry.
        At most EVENT_KEY_COLLISION_ATTEMPTS (3) keys per event; still unresolved
        -> EventPersistenceUnverified -> whole batch rolled back and retained.
    - Exact-set acknowledgement: recorder.begin_write() marks the batch in
      flight; recorder.acknowledge(seqs, reconciled=n) removes exactly the
      verified sequence numbers (never "everything <= last seq"); any exception,
      including a failed/uncertain COMMIT, calls release_write() and nothing is
      acknowledged. Events arriving during the write are never removed.
    - Overflow during a write: an in-flight event shed by the bounded queue is
      counted as dropped only if that write is not confirmed (it may already be
      stored); confirmed ones count as persisted. queue_drops therefore counts
      only real losses.
    - Checkpoint path: _collect_inverter_metrics() now returns True only for a
      verified one-row insert, so a zero-row checkpoint insert adds no marker and
      marks persistence degraded.
    - New counter events_reconciled_existing (lost-ack reconciliations).
    Ordering: queue FIFO order and receipt order are preserved; keys come from
    the monotonic _next_event_time, so for the normal and retry paths DB time
    order equals queue order (tested). Only an event re-keyed after a foreign-row
    collision receives a later key than events already keyed behind it; its
    receipt_at metadata still records the true order.

  QUEUE PERSISTENCE AND RECOVERY GUARANTEES (as implemented)
    - An event leaves the queue only after its own INSERT reported exactly one
      row, or a zero-row INSERT was confirmed (by PK + event_id) to be this
      event's own previously committed row.
    - Any unverified outcome, statement error or COMMIT failure rolls back the
      batch and keeps every event queued; retry after 30 s with stable keys, so a
      committed-but-unacknowledged batch is recognised, not duplicated.
    - Events enqueued during a write are never acknowledged by that write.
    - Losses are explicit: queue_drops counts overflow shed events (an in-flight
      event only if its write was not confirmed) and events discarded when no
      writer can ever run (unrecoverable configuration).
    - A database outage at startup or later does not stop the writer: startup
      retries with 5-300 s back-off; runtime write failures retry every 30 s.
    - NOT guaranteed: survival of queued events across process restart/
      termination (in-memory only); retention beyond the 256-event bound during a
      long outage; dedup across a collision re-key if the foreign-row lookup
      itself is ambiguous (it is then rolled back and retried, not acknowledged).

IMPLEMENTED CHANGES

1. Adaptive telemetry recorder (app/control/adaptive_telemetry.py, new)
    - Fed by InverterMonitor after every successful DESS response, using the
      response the existing poll already fetched. No request and no I/O. Bounded
      CPU work, measured at about 0.005 ms per response.
    - Fingerprints the whole DeviceData payload (sha256, first 16 hex chars).
      Identical payloads count as repeated responses and create nothing.
    - First response after start/restart = baseline; no event (no switching claim
      across a restart or other unobserved gap).
    - Exact observed "Line Mode" <-> "Invert Mode" change -> mode_transition event
      on the response where it is first seen. Other mode changes (e.g. Fault Mode)
      are significant_payload_change with changed field "working_mode"; they are
      never labelled as Line/Invert transitions.
    - Deterministic persistence noise filter (PERSISTENCE_NOISE_BINS, floor
      binning): PV 50 W, battery voltage 0.2 V, charge/discharge current 2 A,
      output 50 W, AC output load 5 %, AC input voltage 10 V. Documented in code
      as persistence filters only, never control/reserve/charger thresholds.
    - A change across a receipt gap > 600 s is labelled sample_continuity="gap".
      Every event carries previous_receipt_at; the switching moment is "between
      the two receipts", never an invented physical time.
    - Bounded queue (default 256), single writer, exact-set acknowledgement of
      verified writes only (see CORRECTIVE PASS, blocker 1).
      On overflow the oldest checkpoint marker is shed first, then the oldest event;
      every drop increments queue_drops. Nothing is queued until a writer attaches
      (TS disabled -> persistence_status "disabled", not silent loss).
    - Checkpoint context (checkpoint_context / checkpoint_interval):
        unknown/stale/naive/malformed/future sun-times    -> 300 s
        sunrise-1h .. sunset+1h (day + transitions)        -> 300 s
        night, not stable observed Line Mode               -> 300 s
        night, validated tuple, observed Line Mode for
        >= 900 s and current receipt (<= 300 s old)        -> 900 s

      (weather_time, sunrise, sunset), all timezone-aware, weather_time <= now,
      age <= OutputPolicyBaseline.forecast_max_age_seconds.

      charging/emergency detail cadence does not multiply marker rows. Each marker
      records payload_changed_since_last_checkpoint.
