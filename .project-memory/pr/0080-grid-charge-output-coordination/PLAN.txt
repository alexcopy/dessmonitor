CONTEXT AND CURRENT BEHAVIOR
    BatteryChargeController owns charger-source policy and may request
    solar_and_mains or solar_only. It does not own inverter output-source
    priority. The current DESS observation path reports working mode, PV,
    output demand, battery voltage/current, charger priority and raw output
    priority, but a reported value is not proof that a setting was physically
    applied.

    Task 0076 already provides the shadow interlock boundary for recovery,
    charger readback, failed trials, lockouts and advisory battery-return
    eligibility. Task 0078 composes that result into fail-closed winter
    diagnostics and does not authorize battery use from unverified reserve.
    Task 0079 provides bounded receipt-time telemetry, repeated/changed
    payload classification, observed Line/Invert transitions, adaptive
    checkpoint history and read-only winter diagnostics. Its timestamp rule
    remains authoritative: DESS Timestamp/gts and DeviceData.device_observed_at
    are not independently verified measurement times.

    Confirmed installation facts are observation inputs only:
    - Output Source Priority reports SBU; catalogue values are Utility=0,
      Solar=1 and SBU=2.
    - Back to Battery reports 26.0 V.
    - Back to Utility is in the 25.x V range, with the exact value masked.
    - The installation is a 24 V system.
    - Read-only queryDeviceCtrlField and queryDeviceCtrlValue are available.
    - Charger Source Priority is independent from Output Source Priority.

    Root-cause hypothesis, explicitly not a proven causal claim:
    while Solar + Mains recovery raises battery voltage toward the reported
    26.0 V SBU return threshold, the inverter remains configured to SBU and
    may autonomously return its load to the battery. The resulting voltage sag
    may return it to Line Mode, after which grid charging continues. Existing
    telemetry can show the sequence, but cannot prove the physical transition
    time, command causality or that any application write caused it.

GOAL
    Define a deterministic, read-only coordination policy that identifies the
    conflict between active mains recovery and an SBU-reported output setting,
    recommends GRID_HOLD while recovery or evidence is unsafe, and mirrors a
    positive solar-return candidate only when the unchanged Task 0076 and
    Task 0078 authority chain has already granted it. This evaluator is not a
    reserve verifier or a second eligibility authority.

    The plan must prevent a future implementation from interpreting a voltage
    rise during grid charging as permission to return output to the battery.
    It must also define the prerequisites and ordering for any separately
    approved future hardware execution without enabling it here.

PROPOSED STATE MACHINE
    The future pure evaluator returns one recommendation state, a desired
    profile label, observed facts, blockers, stable reason codes, cycle
    counters, evidence provenance, and immutable safety markers:

    - EMERGENCY_RECOVERY: the existing charger policy reports active emergency
      recovery or a critical recovery condition. Preserve charging priority;
      this state never waits for optional output optimization.
    - GRID_HOLD: conservative preferred state while grid-assisted charging,
      scheduled long-night recovery, insufficient/unverified reserve, weak or
      unstable PV, sunset approach, stale data, or failed-trial lockout is
      active.
    - SOLAR_RETURN_CANDIDATE: a read-only rendering of an already-authorized
      Task 0076/0078 chain after recovery has ended, measured PV is productive
      relative to measured inverter demand, daylight is valid, charger status
      and readback agree, and the existing dwell/settling rules pass. The
      coordinator never turns a caller's reserve claim into this state.
    - SOLAR_OPERATION: a stronger shadow rendering after the candidate remains
      valid for the existing Task 0076 battery-dwell/settling rules. It is
      still not an execution authorization and cannot issue or queue a write.
      Under the current installation, committed Task 0078 has no trusted
      BMS/shunt integration and therefore this state is unreachable in live
      runtime; this plan does not add one.
    - CHURN_LOCKOUT: repeated short recovery -> Invert -> Line cycles or an
      existing Task 0076 failed-trial/lockout condition blocks voluntary solar
      return until its explicit expiry and evidence requirements pass.
    - FAULT_HOLD: required current data, readback, provenance, reconciliation,
      interlock state or device capability is missing, stale, future-dated,
      contradictory or unavailable.

    Deterministic priority when several conditions apply:
    1. EMERGENCY_RECOVERY and life-support/protection conditions;
    2. FAULT_HOLD for invalid or unsafe evidence;
    3. active CHURN_LOCKOUT;
    4. active grid-assisted recovery or scheduled long-night charging;
    5. manual Utility hold or another existing safety boundary;
    6. GRID_HOLD for recovery completion without all return gates;
    7. SOLAR_RETURN_CANDIDATE;
    8. SOLAR_OPERATION.

    A conflict marker is emitted independently of the recommendation:
    GRID_CHARGING_ACTIVE_WITH_SBU when active recovery or charger readback is
    solar_and_mains while reported output priority is SBU. This marker is an
    observed configuration conflict, not proof that a physical output change
    occurred and not a command request.

TRANSITION AND CYCLE RULES
    - A rising battery voltage while grid charging is active never changes
      GRID_HOLD into a solar-return state.
    - Recovery completion ends the recovery condition only. It does not create
      reserve evidence, satisfy Task 0076, or immediately recommend SBU.
    - Sunrise with weak/unstable PV remains GRID_HOLD. A valid daylight window
      is necessary but not sufficient.
    - The evaluator consumes Task 0079 receipt-time events and labels the first
      observed response of a mode as detection time, never physical transition
      time. A large sample gap is a gap/uncertain sequence, not a guaranteed
      physical cycle.
    - Count a recovery cycle only when ordered observations show a prior
      grid-charging/recovery context, an observed Invert Mode interval, and a
      subsequent Line Mode observation. Missing, stale or out-of-order samples
      cannot create a cycle count.
    - Receipt continuity uses Task 0079's existing SAMPLE_GAP_SECONDS=600:
      consecutive receipt times must be strictly increasing and have a gap of
      at most 600 seconds. Equal, decreasing, unknown or larger-gap times end
      the current sequence; a mode difference across a gap is uncertain and
      cannot count as a transition or cycle. Receipt time is never substituted
      for OutputTelemetry.observed_at.
    - Task 0076 remains authoritative for measurement-time continuity. Its
      existing OutputPolicyBaseline.mode_continuity_max_gap_seconds (300 s)
      segments modes; max_telemetry_gap_seconds (900 s) determines telemetry
      freshness; mode_change_window_seconds (3600 s) bounds recent changes;
      max_mode_changes (4) triggers churn protection; and
      max_failed_trial_escalation (3) bounds failed-trial escalation. The
      coordinator must use the values supplied in that baseline, with the
      existing inclusive comparisons, and must not reconcile an unknown
      observed_at by using receipt time. Thus a trace must satisfy both the
      600-second receipt continuity rule and Task 0076's measurement-time
      rules; otherwise it is uncertain/blocked.
    - Count one recovery cycle only for one ordered sequence containing a
      recovery/grid-charge observation, an observed Invert Mode interval, and a
      later Line Mode observation, with no continuity break under either rule.
      The Line observation closes that sequence. The next sequence starts only
      at a later fresh recovery/grid-charge observation; duplicate payloads are
      ignored for sequence progress, and equal/decreasing/unknown times or a
      gap reset the partial sequence. Repeated cycles do not create a new
      counter: Task 0076's existing `_mode_change_times`,
      `_mode_change_count`, `_failed_trial_events`,
      `_lockout_expiry` and `_churn_lockout_expiry` semantics determine the
      lockout and expiry. The coordinator reports those results rather than
      reimplementing them.
    - Existing Task 0076 fields also own dwell and settling:
      failed_trial_max_seconds, failed_trial_lockout_seconds,
      min_mains_dwell_seconds, min_battery_dwell_seconds,
      post_transition_settle_seconds, churn_lockout_seconds and
      max_churn_lockout_seconds. No coordinator-only cycle window, dwell,
      settling, promotion or anti-flap constant is permitted.
    - A candidate_since value, if ever reached by a separately approved future
      Task 0078 authority chain, is the observed_at of the first current
      snapshot whose exact Task 0076 and Task 0078 evaluations are positive.
      It is reset by any invalid, stale, future, unknown-time, contradictory,
      mode-continuity or receipt-continuity sample; a duplicate payload does
      not advance it or count as a settled sample. Promotion would require
      the existing post_transition_settle_seconds and the existing Task 0076
      settled-segment rules, including its minimum of three valid settled
      samples, followed by min_battery_dwell_seconds. Because current Task
      0078 is never positive, Task 0080 implements no candidate_since or
      promotion path and emits no SOLAR_OPERATION result.
    - Restart behavior is explicit: preserved/reconstructed lockout blocks,
      unavailable restart state fails closed, and a missing history window
      cannot reconstruct a cycle or promotion.
    - A reported output setting, a confirmed read-back, an observed Line/Invert
      mode and an application command are separate fields. No one substitutes
      for another.

COORDINATION INPUTS AND PROVENANCE
    The future evaluator receives immutable values supplied by its caller:
    - current OutputTelemetry and bounded Task 0079 event/history data;
    - existing BatteryChargeController status, desired/observed charger mode,
      emergency/seasonal flags and any fresh charger readback;
    - reported output-priority setting and optional read-only catalogue/value
      observations, each labelled as reported setting evidence only;
    - raw inputs required to recompute Task 0076, plus any reported decision
      only for diagnostics; a reported InterlockDecision is never authoritative;
    - raw inputs required to invoke the unchanged Task 0078 evaluator itself:
      EnergyInputs, ApprovedBands, WinterContext and WinterPolicyConfig. A
      reported WinterDecision is diagnostics-only and is never an authority;
      no reserve field, synthetic flag, verified flag, source label, scalar or
      inspectable record is accepted as an override;
    - explicit daylight/sun-times provenance, receipt age and timestamp
      quality;
    - independent reserve evidence only through the existing approved
      Task 0076/0078 path. Missing or unverified reserve remains blocking;
    - manual operator state from existing arbitration/safety boundaries;
    - bounded restart/lockout state.

    NULL, stale, future, contradictory or unavailable values remain distinct.
    The output must include `shadow_only=True`, `command_issued=False`,
    `hardware_write_attempted=False` and `physical_transition_proven=False`.
    No caller-controlled boolean, source string, scalar reserve or inspectable
    record may override the existing interlock or reserve verification.

    Snapshot-binding contract is mandatory. The evaluator must construct one
    exact current OutputTelemetry object, place that same object in
    InterlockSnapshot.telemetry and InterlockEvaluationInputs.snapshot, then
    call the existing Task 0076 evaluate_interlock with those exact inputs.
    It must require `inputs.snapshot.telemetry is snapshot`; a supplied
    InterlockDecision is diagnostic-only and must be rejected when absent,
    stale or mismatched. The Task 0078 call must pass `interlock=None` and
    the same exact InterlockEvaluationInputs so its own `_bound_interlock`
    path invokes Task 0076; it may not fall back to a caller-supplied
    decision. A mismatch produces FAULT_HOLD with
    INTERLOCK_SNAPSHOT_MISMATCH and cannot produce either positive state.

    Reserve boundary is also mandatory. Current Task 0078 output is always
    fail-closed for live battery use because no trusted BMS/shunt integration
    exists. Externally supplied BMS/shunt observations remain unverified,
    including a structurally valid `synthetic=False` fixture. Task 0080 adds
    no trusted-source flag, certificate, token, verification override or
    reserve mechanism. The current unchanged Task 0078 call returns its
    unverified-reserve result, so both positive coordinator states are
    unreachable in this task. A future trusted integration and any positive
    test require a separate approved amendment to the Task 0078 authority
    chain; this evaluator must then call that amended evaluator from exact raw
    inputs, not accept a precomputed positive fixture. No positive fixture or
    positive battery-use result is part of Task 0080 acceptance.

REQUIRED PROFILES
    GRID_HOLD:
    - Desired profile label: Utility.
    - Keep mains available and preserve BatteryChargeController decisions.
    - Block intentional battery-output return while grid-assisted charging is
      active, even if voltage is at or above 26.0 V.
    - Record actual reported priority separately; SBU plus active recovery is
      a conflict, not a successful Utility setting.
    - Never terminate emergency or scheduled charging to satisfy optimization.

    SOLAR_OPERATION:
    - Desired profile label: SBU, advisory only.
    - Requires valid daylight, stable meaningful measured PV relative to
      measured inverter load, ended grid recovery, consistent charger status
      and readback, the existing Task 0078 eligible decision, the exact
      Task 0076 eligibility recomputed for this snapshot, and the existing
      dwell/settling gates. Current Task 0078 cannot provide that eligible
      decision, so this profile is not reachable in the current runtime.
    - The 26.0 V Back to Battery report is context, not an authorization
      threshold. Voltage rise alone cannot enter this profile.
    - Keep mains available as backup in the future design.

    OPTIONAL PROTECTIVE VOLTAGE CANDIDATE:
    - Model 28.0 V only as a labelled, non-executable comparison candidate.
    - Validate it against the verified 24 V catalogue, approved battery/BMS
      limits and read-only reported values before any future consideration.
    - Explain charging-induced voltage elevation and later sag; do not treat a
      higher threshold as reserve proof.
    - If Utility priority already provides the intended hold, return
      NOT_REQUIRED_WHILE_UTILITY rather than proposing a threshold write.
    - Do not alter unrelated charger voltages or create a write plan in this
      task. Any future controlled use needs separate read-before-write,
      read-back, lock, journal, rollback and uncertain-state approval.
