ROOT CAUSE ASSESSMENT

Root cause: "Voltage and power are never extracted from the canonical
source into the typed pipeline." — CONFIRMED.

The first broken boundary is `build_runtime_read_model()` in
`app/web_runtime_integration.py`. InverterMonitor writes voltage/power to
shared_state, but build_runtime_read_model() never reads shared_state and
has no parameter for inverter data. The runtime_state dict emitted by
build_runtime_read_model() has no inverter key. This cascades: no
runtime_state["inverter"] means the adapter never sees it, the snapshot
never carries it, and the dashboard never renders it.

Is this the first broken boundary? YES. The data exists in shared_state
(written by InverterMonitor) but never enters runtime_state because
build_runtime_read_model() has no inverter input path. Fixing this
boundary (adding an inverter_provider to build_runtime_read_model())
allows the data to flow through the rest of the pipeline.

Does the target flow remove the defect rather than compensate downstream?
YES. The plan proposes adding InverterReadSnapshot, _parse_inverter(),
inverter fields on all adapter/snapshot types, and an inverter_provider
at the runtime_state level. This is adding the canonical source, not
compensating downstream.

Has the plan combined two independent root causes? NO. The plan explicitly
separates:
- Root cause #1 (this PR): inverter voltage/power not in typed pipeline
- Root cause #2 (deferred PR0034m): Tuya 1106 isolation budget exhaustion
  and run_coroutine_threadsafe same-loop blocking
These are correctly identified as independent: different data sources
(DESS API vs Tuya Cloud), different data types (inverter metrics vs
temperature/binary state), different scope.

Is a split into PR0034l and PR0034m required? YES — the plan declares
PR0034m as deferred. This is correct. Merging both would:
1. Create a single PR with two unrelated typed contracts (InverterReadSnapshot
   vs sensor polling state)
2. Require Tuya SDK mocking (different test infrastructure)
3. Delay the inverter fix while solving a harder Tuya reliability problem
4. Conflate DESS API telemetry with Tuya polling defects

TYPED CONTRACT ASSESSMENT

The plan defines InverterReadSnapshot with proper domain separation:

- Domain ownership: InverterReadSnapshot belongs in
  app/control/control_state_snapshot.py alongside LoadControlSnapshot and
  SensorReadSnapshot. CONFIRMED: This is a new canonical domain object for
  DESS inverter electrical telemetry, NOT a modification of SensorReadSnapshot
  (which remains temperature-only with unit default "celsius").

- Identifier semantics: snapshot_id (str, primary identifier for the inverter
  reading instance), observed_at (ISO timestamp, nullable).

- Metric names: battery_voltage, battery_soc, battery_charging_current,
  battery_discharging_current, pv1_voltage, pv1_power, pv2_voltage, pv2_power,
  pv_total_power, output_voltage, output_power, output_apparent_power,
  ac_input_voltage, ac_input_frequency, ac_output_load, working_mode,
  battery_status, pv_status, mains_status, load_status.

- Nullable numeric values: ALL numeric fields are float | None with default
  None. CONFIRMED: None represents missing/unavailable data, never zero.

- Units: V for voltage, W for power, VA for apparent power, A for current,
  % for SOC and load, Hz for frequency. Explicitly documented per field.

- observed_at: str | None = None — ISO timestamp, nullable.

- Freshness: str (computed from observed_at relative to snapshot creation).
  Default "".

- Status: str (related to inverter comms). Default "".

- Communication status: Not explicitly listed. The plan uses source="dess"
  and freshness for data quality. This is acceptable for an inverter which
  is a single device (not a fleet of Tuya sensor devices).

- Serialization boundary: All fields are web-safe (float | None, str). No
  datetime objects at the web boundary. FastAPI auto-serializes frozen
  dataclasses.

- UI null/stale behavior: Null renders N/A, never numeric zero. CONFIRMED
  by plan: "Dashboard renders N/A, never numeric zero."

This is NOT inserting voltage/power into SensorReadSnapshot (temperature
model). CONFIRMED: SensorReadSnapshot remains temperature-only with
unit="celsius" default. InverterReadSnapshot is a separate type.
