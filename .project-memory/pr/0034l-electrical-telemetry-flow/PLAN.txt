TITLE
PR 0034l — Inverter Electrical Telemetry Projection into Control State Snapshot

INCIDENT
The authenticated dashboard at GET /control/state does not display expected
voltage and power values (battery_voltage, output_power, pv_total_power,
output_voltage, pv1_voltage, pv2_voltage, ac_input_voltage, pv1_power,
pv2_power).

The runtime log also contains:
- Tuya API response code 1106 ("permission deny");
- updater warning "Isolation budget exceeded — giving up".

These are unrelated root causes sharing no common data path:
- Voltage and power are DESS inverter metrics written by InverterMonitor to
  shared_state.  They never enter the typed control snapshot pipeline.
- Code 1106 and isolation-budget exhaustion are Tuya sensor polling issues.
  They affect sensor temperature telemetry only, not inverter metrics.

TUYA POLLING PATH (sensor telemetry — not inverter voltage/power)

_requested parents -> build_poll_targets() returns ordered list of enabled
  parent IDs (both LOAD and SENSOR classified).
  -> _get_healthy_parents() filters out quarantined parents.
  -> _poll_and_process() calls device_manager.get_device_list_status(parent_ids).
  -> If success=false and code=1106:
       Single parent -> _mark_permission_denied() with exponential backoff.
       Multi-parent -> _bisect_failed() recursively halves the batch.
         Each bisection increments _isolation_budget.
         When _isolation_budget > MAX_ISOLATION_REQUESTS (16):
           log: "Isolation budget exceeded — giving up"
  -> On success: _process_result() iterates result per parent.
       LOAD devices: update observation from state_property.
       SENSOR devices: _update_sensor_telemetry() extracts temperature
         from candidate properties (temp_current, va_temperature, etc.).
  -> If sensor parent has no telemetry property in batch response:
       _schedule_sensor_individual_fallback() triggers an RPC per parent
       via run_coroutine_threadsafe with get_running_loop (same-loop pattern).
  -> Quarantined parents with status=permission_denied are retried at
     exponentially increasing intervals (300s -> 600s -> ... -> 3600s max).

Note: The Tuya path handles only sensor temperature telemetry and device
      binary state observations.  It does NOT handle voltage or power.
      Voltage and power come exclusively from the DESS API.

ROOT CAUSE
Inverter electrical telemetry (voltage and power) is never extracted from
shared_state into the typed ControlStateSnapshot pipeline.  There is no
InverterReadSnapshot type, no runtime_state["inverter"] key in
build_runtime_read_model(), no parsing in the snapshot adapter, no
propagation through ControlStateSnapshot, and no rendering in the dashboard.

The dashboard displays:
- Load state (ON/OFF/UNKNOWN per device, from Tuya polling)
- Sensor temperature (water temp, from Tuya polling via TelemetryRegistry)
- Configured load wattage (load_in_wt, from YAML config)

It does NOT display any of:
- battery_voltage (V)
- output_power or output_apparent_power (W / VA)
- pv_total_power, pv1_power, pv2_power (W)
- output_voltage, pv1_voltage, pv2_voltage, ac_input_voltage (V)
- battery_capacity / SOC (%)
- battery_charging_current, battery_discharging_current (A)
- ac_output_load (%)
- ac_input_frequency (Hz)
- working_mode (string)
- mains_status (string)
- inverter_summary (string)

This is root cause #4: "Voltage and power are never extracted from the
canonical source into the typed pipeline."

Adjacent defects NOT part of this root cause:
- Tuya 1106 (code 1106) and isolation-budget exhaustion are sensor polling
  reliability issues.  They affect water temperature telemetry only, not
  inverter voltage/power.  The data sources are completely separate:
  DESS API vs Tuya IoT cloud.
- The configured_load_watts vs live output_power distinction is a domain
  concept, not a bug.  They measure different quantities.
- Missing ambient temperature is weather-service telemetry, not electrical.

DOMAIN MODEL / TYPED CONTRACT

The target values are INVERTER-LEVEL electrical telemetry.  They belong in a
new typed projection: InverterReadSnapshot.

This is NOT sensor telemetry (temperature), NOT load observation (ON/OFF),
and NOT a shared_state web fallback.  It is a new canonical domain object
representing the single DESS inverter's current operating state.

Field semantics for InverterReadSnapshot:

  identifier       type          default    unit    nullable  description
  snapshot_id      str           ""         —       no        snapshot identifier
  observed_at      str | None    None       —       yes       ISO timestamp
  battery_voltage  float | None  None       V       yes       battery bank voltage
  battery_soc      float | None  None       %       yes       state of charge
  battery_charging_current  float | None  None  A   yes       charge current
  battery_discharging_current float | None  None  A  yes      discharge current
  pv1_voltage      float | None  None       V       yes       PV1 voltage
  pv1_power        float | None  None       W       yes       PV1 power
  pv2_voltage      float | None  None       V       yes       PV2 voltage
  pv2_power        float | None  None       W       yes       PV2 power
  pv_total_power   float | None  None       W       yes       combined PV power
  output_voltage   float | None  None       V       yes       AC output voltage
  output_power     float | None  None       W       yes       active output power
  output_apparent_power float | None  None  VA      yes       apparent output power
  ac_input_voltage float | None  None       V       yes       AC input (grid) voltage
  ac_input_frequency float | None None      Hz      yes       AC input frequency
  ac_output_load   float | None  None       %       yes       output load percentage
  working_mode     str           ""         —       no        inverter working state
  battery_status   str           ""         —       no        battery status string
  pv_status        str           ""         —       no        PV status string
  mains_status     str           ""         —       no        mains status string
  load_status      str           ""         —       no        load status string
  freshness        str           ""         —       no        source freshness
  source           str           "dess"     —       no        data source label

Freshness is computed from observed_at relative to the snapshot creation time.
When observed_at is missing, freshness is "unavailable".

All voltage fields are in volts (V).  All power fields are in watts (W) except
output_apparent_power (VA).  All current fields are in amperes (A).  All
percentage fields are in percent (%).  Frequency is in hertz (Hz).

Null values represent missing/unavailable data.  Dashboard renders N/A, never
numeric zero.

InverterReadSnapshot belongs in app/control/control_state_snapshot.py,
alongside LoadControlSnapshot and SensorReadSnapshot.  It is a frozen
dataclass with all fields keyword-only.

No existing type carries voltage/power.  SensorReadSnapshot is designed for
temperature (unit defaults to "celsius") and has no voltage or power fields.
Adding voltage/power to SensorReadSnapshot would conflate two orthogonal
telemetry domains (water temperature vs inverter electrical metrics).

ASYNC SAFETY ASSESSMENT
The inverter data source (InverterMonitor) uses asyncio.to_thread for
blocking DESS API calls and writes to a thread-safe shared_state singleton.
No run_coroutine_threadsafe pattern exists in the inverter path.

The Tuya status_updater_async.py contains:
  _schedule_sensor_individual_fallback() at line 451-457:
    asyncio.run_coroutine_threadsafe(
        self._do_individual_fallback(...),
        asyncio.get_running_loop(),
    ).result(timeout=TUYA_RPC_TIMEOUT)

This is the dangerous same-loop pattern: run_coroutine_threadsafe targeting
the SAME running event loop from inside that same loop.  This blocks the
polling coroutine indefinitely if the fallback RPC hangs (despite timeout,
the blocking .result() holds the thread while the loop is running).

However, this defect affects Tuya sensor fallback, NOT inverter electrical
telemetry.  It is excluded from PR0034l scope and is the candidate root
cause for PR0034m (Tuya async fallback and isolation hardening).

No other dangerous async patterns were found in the inverter data path.
InverterMonitor uses asyncio.to_thread (safe) and does not block the loop.

RISKS
1. InverterMonitor writes to shared_state.  If the web layer reads
   shared_state directly (instead of a dedicated provider), this creates
   coupling to the global dict.  Mitigation: run.py creates a dedicated
   inverter_holder (a simple thread-safe dict or callback) that
   InverterMonitor writes to and the web provider reads.  shared_state
   is not read in the web layer.

2. InverterMonitor polls every 60s.  The dashboard polls every 5s.  If
   the inverter holder is empty between polls, the dashboard shows null
   values.  This is correct behavior (N/A displays).  No synthetic
   fallback or zero-fill should be added.

   otherwise empty snapshot with inverter data should not be UNKNOWN.
   The plan requires this adjustment in build_control_state_snapshot().

   the visual layout.  The plan limits this to a new card row (summary
   cards inline with existing totals).  Full tab redesign is deferred to
   PR0039+.

5. BatteryOperatingWindow in the policy engine uses voltage thresholds
   (24.5V, 25.0V, etc.), not live battery_voltage.  No live value flows
   into the policy engine from this PR.  The live battery_voltage is
   for display only until a future PR wires it into policy context.
