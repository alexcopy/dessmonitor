BLOCKING FINDINGS

1. The planned coordinator history is not the history required by Task 0080.

Plan lines 93–95 require reuse of ShadowOutputMonitor.history. The current
monitor stores a deque of OutputTelemetry objects only (shadow_output_monitor.py
lines 34 and 72–90). It retains a point only when device observed_at is known
and ordered. It does not retain the separate received_at/fingerprint pair,
charger observation, or policy provenance needed by Task 0080.

The coordinator's actual contract requires a tuple of ReceiptObservation
objects, each containing an InterlockSnapshot, a separate received_at and a
non-empty fingerprint (grid_charge_output_coordination.py lines 30–35 and
80–124). Its duplicate, receipt-gap, measurement-gap and recovery-cycle
decisions therefore cannot be implemented from ShadowOutputMonitor.history.
Under the current runtime, WinterRuntimeDiagnostics deliberately sets
OutputTelemetry.observed_at=None (winter_runtime_diagnostics.py lines 185–197),
so this source is normally empty as well.

The acceptance tests requested at plan lines 248–255 would consequently test
an in-memory synthetic path rather than the actual DESS observation path, or
would silently lose the history needed for duplicate/gap semantics.

Minimal required correction: define in the plan the bounded in-memory
ReceiptObservation history and its owner within the existing allowlist. It
must be appended once for every successful response, preserve separate
receipt time and unverified device time, carry the actual charger/policy
metadata and a stable response fingerprint, and explicitly reset or mark
uncertainty for duplicate, stale, future, out-of-order and gap cases. It must
not use dashboard data or substitute receipt time for measurement time. If
the existing recorder is to own this history, the plan must specify the typed
adapter/API; otherwise the plan must state the bounded diagnostic-local deque.
No database table or second DESS polling loop is needed.

2. The charging-policy provenance provider named by the plan does not exist.

Plan lines 96–102 require a read-only provider exposing the
BatteryChargeController's runtime status, provenance and verification flag.
The current BatteryChargeController has no such typed provider. Its current
published shared_state dictionary (battery_charge_controller.py lines
179–194) contains state, desired/observed charger modes and error fields, but
no provenance or verified flag. Its command methods remain in the same
controller (lines 196–224). The current WinterRuntimeDiagnostics input path
creates an InterlockSnapshot with the default unknown charger and a null
policy (winter_runtime_diagnostics.py lines 200–205).

This matters because evaluate_coordination requires fresh, non-UNKNOWN,
verified ChargePolicyStatus metadata and DEVICE_READBACK charger evidence;
otherwise it must produce FAULT_HOLD. Ordinary DESS telemetry is correctly
forbidden from being promoted to either readback or verified policy status,
but the plan does not say how the actual runtime status reaches the evaluator.
It also does not specify how setting freshness is represented without using
receipt_at as an unverified device measurement time.

Minimal required correction: specify the read-only adapter and its exact
mapping in an allowed file. With the current sources, the safe mapping is
runtime-status provenance with verified=False unless an already-approved
source supplies an explicit verification flag; ordinary DESS charger/output
telemetry must remain UNKNOWN/UNVERIFIED, not DEVICE_READBACK. The plan must
state that this intentionally leaves conflict/readback-dependent results
blocked when no approved source exists, while still displaying the reported
raw value separately. If a verified provider cannot be built without changing
BatteryChargeController, the plan must amend the allowlist before
implementation rather than implying that the provider already exists.

REQUIRED CALLBACK ORDER

The safety intent is sound, but the implementation acceptance must assert the
actual sequence. In the current monitor, the existing observation observer
runs before solar_controller.tick() and BatteryChargeController.tick(), and
the existing ShadowOutputMonitor runs afterward (inverter_monitor.py lines
35–75). The new coordinator callback must be a separate post-charge callback:

successful DESS fetch → existing observer/telemetry hand-off → solar tick →
BatteryChargeController.tick() → coordinator callback → existing shadow
monitor handling (or an explicitly documented equivalent).

The existing observer must not be moved, replaced or made dependent on the
coordinator. The new callback needs its own exception boundary and rate-
limited logging, and its failure must not skip the charger tick. Add an
ordering test with event markers and a failure test proving that both the
charger and shadow monitor still run. This is required to make plan lines
110–116 and 194–197 executable, not merely descriptive.

RESOLUTION OF PRIOR BLOCKERS

1. Bounded ReceiptObservation history — RESOLVED

PLAN.txt lines 91–113 now explicitly require a diagnostic-local bounded deque,
not ShadowOutputMonitor.history. It appends exactly one ReceiptObservation for
each successful DESS response, including duplicates, and binds each entry to:

- the exact single normalized OutputTelemetry object;
- a separate received_at receipt timestamp, without substituting it for device
  measurement time;
- the AdaptiveTelemetryRecorder stable payload fingerprint through a new
  read-only latest_fingerprint accessor;
- immutable charger and charge-policy metadata carried in the same interlock
  snapshot; and
- explicit uncertainty for missing fingerprints, unknown device time, stale or
  out-of-order receipts, duplicates and gaps.

PLAN.txt lines 134–140 additionally require the post-charge path to use that
same object and reject a missing or mismatched pending response as FAULT_HOLD.
The acceptance contract at lines 291–293 requires one-entry-per-response,
fingerprint reuse, duplicate/gap/unknown-time continuity checks, and exact
OutputTelemetry identity assertions. The plan forbids a second poller, durable
lockout store, dashboard reconstruction, or receipt-time substitution.

2. Charge-policy/provenance adapter — RESOLVED SAFELY

PLAN.txt lines 119–126 now define the adapter against the current shared_state
charge_policy_status mapping: state, emergency flag, and desired charger mode
are copied as read-only values; provenance is ChargePolicyProvenance.RUNTIME_STATUS;
verified is explicitly False; and evaluated_at is explicitly None because the
current BatteryChargeController publishes neither a verification flag nor a
policy timestamp. Missing or malformed fields become UNKNOWN/None.

This mapping intentionally cannot satisfy Task 0080's verified policy gate and
therefore remains blocked at FAULT_HOLD where approved policy provenance is
absent. It does not alter BatteryChargeController or treat a desired command
as observed state. PLAN.txt lines 114–118 and 127–130 separately require raw
DESS charger/output-priority telemetry to remain display-only UNKNOWN/
unverified evidence, never DEVICE_READBACK, and prohibit
queryDeviceCtrlField/queryDeviceCtrlValue calls.

The current Task 0080 types confirm that this is the conservative mapping:
ChargePolicyStatus accepts the named fields and has verified=False by default,
while evaluate_interlock requires a fresh policy timestamp, verified=True,
non-UNKNOWN provenance, and DEVICE_READBACK charger evidence before using the
metadata. The amendment therefore keeps the known runtime limitation visible
without inventing verification.

3. Callback order and exception isolation — RESOLVED

PLAN.txt lines 142–153 specify the executable order:

successful DESS fetch → existing observation/telemetry hand-off → solar tick →
BatteryChargeController.tick() → post-charge coordinator callback → existing
ShadowOutputMonitor handling.

The coordinator callback is explicitly separate, has its own exception
boundary and rate-limited logging, adds no DESS request, and cannot skip,
cancel, move, suppress, or replace the charger tick. The acceptance tests at
lines 286–302 require event-marker ordering plus a failure case proving that
both charger and shadow callbacks still run after a coordinator exception.
This is concrete and executable within the listed service/inverter_monitor.py
allowlist.
