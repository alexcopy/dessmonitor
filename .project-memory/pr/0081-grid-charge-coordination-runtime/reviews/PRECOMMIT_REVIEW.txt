BLOCKERS

1. Exact post-charge observation identity is not enforced.

   In app/control/winter_runtime_diagnostics.py:447-465,
   observe_coordination() accepts any data object when its received_at equals
   the pending snapshot's received_at. It does not compare the source
   response identity, normalized measurements or the fingerprint that is
   passed to the post-charge callback. The ReceiptObservation is then built
   from the pending telemetry but charger/output fields are read from the
   potentially different data object.

   Independent reproduction: after observe() with a Line Mode response at one
   receipt time, a different Invert Mode/PV/output response at the same receipt
   time and a different fingerprint was accepted and produced a coordination
   payload instead of COORDINATION_OBSERVATION_IDENTITY_UNAVAILABLE. It stayed
   FAULT_HOLD, but the plan requires exact identity binding and forbids mixing
   metadata from different responses.

   Minimal fix: retain a source identity/fingerprint binding when observe()
   creates the pending inputs, and require the post-charge hand-off to match
   it before attaching charger/policy metadata or appending history. Add a
   regression test for same-receipt, different-payload/fingerprint input.

2. The dashboard contract is incomplete and does not render the mandatory
   shadow-only label.

   The plan requires the authenticated panel to show the desired output
   profile, coordinator blockers/reason codes and missing evidence, lockout
   expiry when present, and the persistent label “SHADOW ONLY — NO HARDWARE
   COMMANDS”. The implementation's renderWinterCoordination() in
   app/web/static/dashboard.js:1000-1021 renders state, priority, charger,
   policy, cycles, mode changes, continuity and a boolean conflict only. It
   omits desired_profile, coordination reasons/blockers and
   lockout_expires_at. The existing template note says “Shadow-only
   diagnostic. It issues no commands...” but does not provide the mandated
   persistent label. The UI test does not assert these required fields.

   There is also a semantic conflict bug at
   app/control/winter_runtime_diagnostics.py:426: conflict is set only for
   OUTPUT_SETTING_CONTRADICTORY and not for the coordinator's explicit
   GRID_CHARGING_ACTIVE_WITH_SBU reason. The payload must preserve that
   conflict marker whenever the evaluator supplies it, while still keeping
   the result advisory.

   Minimal fix: render the omitted payload fields and add the exact static
   shadow-only label; derive conflict from both approved conflict reason codes
   and extend the UI assertions. Missing values must remain unavailable.

3. The callback regression test does not prove the complete required order or
   next-poll continuity.

   tests/test_shadow_output_monitor.py:341-359 checks observer → charger →
   coordinator → shadow, but its helper never supplies a solar_controller and
   stops after one poll. It therefore does not independently prove
   observer → solar → charger → coordinator → shadow, nor that a coordinator
   exception permits the next inverter poll. The implementation's source order
   is currently correct, but the approved plan explicitly requires event-marker
   coverage for solar and exception isolation through the next poll.

   Minimal fix: add a solar tick marker to the ordering test and run at least
   two polls in the coordinator-failure test, asserting both subsequent fetch
   and normal callbacks.

TARGETED RECHECKS

1. SAME-RECEIPT IDENTITY BINDING — BLOCKER REMAINS

The corrected path now rejects a different receipt or a different supplied
fingerprint before appending coordination history. The new regression test for
different payload plus different fingerprint passes, and that rejection does
not append mixed metadata.

However, app/control/winter_runtime_diagnostics.py still treats matching
received_at plus a matching caller-supplied fingerprint as sufficient identity.
It does not compare the post-charge data payload or a canonical normalized
payload identity with the payload used by observe(). An independent read-only
reproduction supplied a Line Mode response to observe(), then supplied a
different Invert Mode/PV response at the same receipt time while reusing the
same fingerprint. The callback was accepted, returned an ordinary FAULT_HOLD
decision, and appended a ReceiptObservation whose telemetry came from the
pending response while charger/output metadata came from the post-charge
response. The mixed entry is observable in the diagnostic history.

This violates the approved exact-response binding and the requirement that a
same-receipt different-payload/fingerprint handoff fail closed without
appending mixed metadata. A fingerprint is useful evidence, but accepting it
as an unchecked caller claim leaves the stale/reused-fingerprint path open.

Minimal correction: retain a canonical identity derived from the exact
normalized response used by observe(), and require the post-charge response to
match that identity before attaching charger/policy metadata or appending
history. Add a regression test for same receipt, different payload, and a
reused/identical fingerprint; assert both the identity reason and unchanged
history length.
