REVISION 3 (PLAN_REVIEW.txt remaining blocker: in-flight cutover race)
SUPERSEDED by revision 4. Kept unchanged below as a historical record. The
reviewer found two valid counterexamples: (1) t_exit came from the operator's
clock but was compared with the database server's xact_start, so clock skew could
leave out an in-flight transaction; (2) the /proc scan treated an unreadable
cmdline as an absent process. Either could produce a false "did not commit".
Files changed: .project-memory/JOURNAL_V2_OPERATOR_RUNBOOK.md (step 6), this report.
PLAN.txt, reviews/PLAN_REVIEW.txt, application code and migration SQL not modified.
- Step 6 cutover command now runs in one named pod ($POD) and records the pod and time.
- Any exception, timeout, lost acknowledgement or connection failure is UNKNOWN.
  The runbook states why a fresh v1 read is not proof: the cutover may still be
  waiting on the advisory lock (no server-side timeout), a dropped kubectl exec
  does not reliably stop the process, a lost connection does not immediately stop
  the backend, and changed_at is the CLI's start time (taken before the lock wait),
  so a late commit can write an early changed_at.
- 6a: a fresh read showing v2 that passes the state/event consistency checks means
  committed (go to step 7). v2 without those means UNKNOWN. v1 means go to 6b.
- 6b (all required, in order): 6b-1 the client process in the recorded pod has
  ended (/proc check, because the image has no ps; or the pod was deleted or its
  container restarted); 6b-2 drain check: every client backend transaction that
  started before t_exit has finished. This is checked on the server as a superuser
  or pg_read_all_stats member and fails closed otherwise. It does not need to pick
  out the CLI's backend, which shares the worker role and pod and has no
  application_name. 6b-3 a new read shows v1 with an unchanged changed_at. Only
  then is non-commit confirmed, and a new cutover needs a separate operator decision.
- Unidentifiable pod or process, unreachable pod, insufficient visibility, or a
  drain not passing within ~15 minutes: stay UNKNOWN and escalate. While UNKNOWN:
  no retry, no --allow-empty-state, no rollback, no manual mode change, no
  terminating sessions.
- Basis: cutover_to_v2 runs lock, writes and COMMIT in one explicit transaction
  (app/control/adaptive_journal_v2.py:449-494). PostgreSQL commits only on a
  client COMMIT; a backend whose client is gone aborts its open transaction.
- Validation, all on new uniquely named local throwaway containers, removed
  afterwards (no production or shared database; no real CLI cutover executed).
  postgres:16-alpine with migrations 001 and 002 applied; the drain block and the
  /proc block were extracted verbatim from the runbook. The simulated cutover sends
  BEGIN, pg_advisory_xact_lock(5276389241085182), UPDATE mode, COMMIT one
  statement at a time, like asyncpg:
    S1 cutover waiting on the lock, client alive: fresh read v1; drain FAIL (exit 3)
       listing the waiting backend (wait_event advisory); after the lock was released
       the cutover committed and the read became v2. So the v1 read was not proof.
    S2 committed, output discarded (lost acknowledgement): 6a read v2.
    S3 client killed (SIGKILL) while its backend waited on the lock: client gone,
       backend still listed waiting, drain FAIL (exit 3); after the holder released
       the lock, drain PASS (exit 0) and the read stayed v1 with an unchanged changed_at:
       the orphaned backend did not commit.
    S4 identification/visibility: checker without pg_read_all_stats sees NULL
       state/xact_start and "<insufficient privilege>"; the drain refused (exit 3,
       "cannot see all sessions"). With full visibility, an unrelated transaction
       started before t_exit also keeps the drain at FAIL (conservative, no
       identification needed).
    python:3.12-slim (the Dockerfile base): ps is not present. The /proc check printed
       NO_CUTOVER_PROCESS with only "status" and a decoy "other.py cutover" running,
       listed the running "adaptive_journal_v2.py cutover" process (not itself),
       and printed NO_CUTOVER_PROCESS after that process exited.
