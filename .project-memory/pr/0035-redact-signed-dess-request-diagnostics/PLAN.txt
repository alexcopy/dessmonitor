CURRENT FACTUAL STATE
The following findings are confirmed against the current repository at HEAD cd0847a:

1. app/api.py DessAPI class constructs signed DESS request URLs and exposes them
   through three diagnostics paths (lines 235, 238, 343). Each URL contains
   sensitive credential and device-identifying parameters.

2. The sensitive parameters present in the logged URLs include:
   - sign (SHA-1 signature hash)
   - salt (timestamp-based salt)
   - token (DESS API session token)
   - usr (email address, used during authentication)
   - company-key (organization identifier)
   - pn (product number/serial)
   - sn (device serial number)
   - devcode (device code)
   - devaddr (device address)
   - The full DESS API base URL, which includes the provider hostname
   - App client/version identifiers (_app_client_, _app_id_, _app_version_)

3. The three leakage paths are:
   Path A (line 235): self.logger.info(f"[API] Выполняем запрос: {url}") — logs the
     complete signed URL at INFO level. The logger is wired to the DessAPI's
     dess_log logger, which is also given a loki_handler(), meaning signed URLs
     flow to Loki-formatted logs (logs/loki.log) and may be shipped to Grafana.
   Path B (line 238): print("The request URL >>>", url, "\n>>> ", end="", flush=True)
     — writes the complete signed URL to stdout. Container stdout is captured by
     Kubernetes and sent to log aggregation.
   Path C (line 343): self.logger.info(f"[WEB] Выполняем запрос: {url}") — logs the
     complete fallback URL (same parameter set, different base URL and action) at
     INFO level through the same logger.

4. Wrapped exception messages (lines 249-250 in _do_api_request, line 351 in
   fetch_device_data_fallback) do NOT contain the URL directly — they wrap generic
   strings. The exception chain is safe:
     RuntimeError(f"Ошибка запроса: {e}") where e is the exception from the urllib
     call, which is typically a URLError/HTTPError without the full URL in its
     str representation in standard Python.

5. The fallback path (fetch_device_data_fallback) constructs the URL string
   separately from the primary path (lines 337-341). Both paths independently
   log the full URL.

6. The primary path (fetch_device_data → _do_api_request) constructs the URL
   by joining API_BASE, sign, salt, token, and query parameters into one f-string
   (lines 229-233). The query_str is built from a params dict that includes
   action, i18n, pn, devcode, devaddr, sn, source, _app_client_, _app_id_,
   _app_version_.

7. The authentication path (authenticate → _do_api_request with need_auth=False)
   flows through the same _do_api_request method and logs the signed URL for
   the authSource action — which additionally includes usr and company-key.

8. The fallback path constructs action_str by quoting pn, devcode, devaddr, sn
   individually rather than using the dict-based approach of the primary path.

9. No other Python file in the repository constructs, logs, or prints DESS API
   URLs. The DessAPI class is instantiated only in run.py at module level and
   passed to InverterMonitor.

ROOT CAUSE
app/api.py logs and prints fully constructed signed DESS API request URLs as
diagnostics. These URLs contain the following categories of sensitive data:

1. Authentication credentials: sign (signature proving request authenticity),
   salt (tied to secret+token), token (session token), and during authentication
   also usr (email) and company-key.

2. Device-identifying serial numbers: pn (product number), sn (serial number),
   devcode, devaddr.

3. Application metadata: _app_id_, _app_client_, _app_version_ (these are
   constants but leak internal application identification).

Because the logger instance used by DessAPI is registered with a Loki log handler
(via app/logger.py loki_handler), the signed URLs flow to structured log files
(logs/loki.log) that are shipped to the Loki/Promtail pipeline, making them
persistent in log aggregation infrastructure. The stdout print at line 238
captures the signed URL in container stdout, which Kubernetes captures by
default.

The fix must redact exactly the credential and device-identifying query parameters
from the logged/printed representation of the URL while preserving the actual URL
passed to urllib.request.urlopen unchanged.

PROPOSED DESIGN

Add a single private static method to DessAPI that produces a redacted-safe
representation of a URL string, leaving only the scheme, host, path, and
safe query parameters visible. Credential and device-identifying parameters
are replaced with a controlled sentinel.

Safe diagnostic contract:
  - Scheme and host remain visible (e.g., "https://api.dessmonitor.com")
  - Path remains visible (e.g., "/public/")
  - Action parameter remains visible (e.g., "action=queryDeviceLastData",
    "action=authSource", "action=updateToken", "action=querySPDeviceLastData")
  - All other query parameters are replaced with "REDACTED" or equivalent.
  - Exception: i18n parameter may remain visible as it contains no sensitive
    data (value is "en_US").

Implementation approach in DessAPI:

  @staticmethod
  def _redact_url(url: str) -> str:
      """Return a diagnostics-safe representation of a signed DESS URL.

      The scheme, host, path, and action parameter remain visible.
      All credential, device-identifying, and app-identifying parameters
      are replaced with a fixed sentinel string.

      The actual URL for the HTTP request is never changed.
      """
      REDACTED = "REDACTED"
      SENSITIVE_QUERY_PARAMS = frozenset({
          "sign", "salt", "token", "usr", "company-key",
          "pn", "sn", "devcode", "devaddr",
          "_app_client_", "_app_id_", "_app_version_", "source",
      })
      # Parse the URL into scheme, netloc, path, params, query, fragment
      # Reconstruct with safe params only
      ...

Replace:
  self.logger.info(f"[API] Выполняем запрос: {url}")
with:
  self.logger.info(f"[API] Выполняем запрос: {self._redact_url(url)}")

Replace:
  print("The request URL >>>", url, "\n>>> ", end="", flush=True)
with:
  logger.debug("[API] Request URL: %s", self._redact_url(url))
  # OR completely removed — see design decision below

Replace:
  self.logger.info(f"[WEB] Выполняем запрос: {url}")
with:
  self.logger.info(f"[WEB] Выполняем запрос: {self._redact_url(url)}")

Design decision on stdout print:
  The line 238 print statement has no value after redaction — even a redacted
  URL provides no useful real-time diagnostic that the logger does not already
  provide. The safest implementation is to remove it entirely. If the operator
  needs request-level diagnostics, the logger provides them at INFO level with
  the redacted URL.

Design decision on URL redaction approach:
  Option A — parse with urllib.parse.urlparse, reconstruct query string filtering
  out sensitive params. Pros: correct, handles any URL structure. Cons: slightly
  more code.
  Option B — replace each sensitive parameter name in the query string using
  regex. Pros: simple. Cons: could match partial parameter names, fragile if
  parameter values contain "&" or "=" (URL-encoded).
  Option C — parse with urllib.parse.urlparse, use urllib.parse.parse_qs, filter
  keys, rebuild with urllib.parse.urlencode. Pros: correct, handles encoding.
  Cons: changes parameter ordering (parse_qs returns dict). The ordering
  difference does not matter for diagnostic logging.

  Recommended: Option C (urllib.parse.urlparse + parse_qs + filter + urlencode).
  Preserves the action/i18n parameters. Replaces all SENSITIVE_QUERY_PARAMS
  values with sentinel.

RISKS AND WARNINGS
- urllib.parse.parse_qs changes parameter ordering because it returns a
  dict (Python 3.7+ preserves insertion order). The safe diagnostic URL may
  have parameters in a different order than the original signed URL. This does
  not affect any behavior — the log output is strictly diagnostic.
- If parse_qs encounters a parameter with multiple values (unlikely for
  signed DESS URLs), it returns a list. The urlencode will produce
  key=value1&key=value2. This is safe but may look unusual. Since all
  sensitive params are replaced with REDACTED, multi-value parameters
  are irrelevant.
- urlopen is called with the original full URL — the redaction is only
  in the logged/printed representation. Verify this through the validator.
- If future code adds new logging paths with the URL, the fix must be
  extended. This PR covers only the three currently known leakage paths.
