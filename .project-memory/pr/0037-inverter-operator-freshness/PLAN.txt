TITLE
PR 0037 — Inverter Operator Metrics and Freshness

INCIDENT
The operator dashboard is improved after PR0036 (compact layout, source indicator,
load tabs) but still needs inverter-centric operational refinement:

- Output power is shown as plain text ("800 W") with no severity color that would
  tell the operator at a glance whether the inverter is lightly loaded, heavily
  loaded, or overloaded.
- The inverter-reported timestamp (the DESS API's native time) is not shown
  separately from the dashboard snapshot timestamp — the operator cannot tell
  when the inverter itself last reported.
- The inverter-reported timestamp is stored as a naive local-time string
  ("2026-07-25 12:00:00") with no timezone marker.  When rendered by
  JavaScript Date parsing, behaviour is inconsistent across browsers.
  The operator expects Europe/London timezone display.
- There is no freshness indicator for inverter data — the operator cannot see
  at a glance whether the inverter is still sending fresh data or has gone
  silent.
- Charge current and discharge current are already present in the inverter
  detail row (added by PR0036), so no new visibility work is needed there.

Weather forecast and prediction were also requested but are separate
data-source features that must be deferred to a separate PR.

POWER SEVERITY CONTRACT

Thresholds derived from typical inverter specifications for a 3-3.5 kVA
hybrid inverter (the known operating range for this deployment):

- output_power is null or undefined -> severity "unknown"
- output_power <= 1700 W (approx 50% of ~3.5 kVA rated capacity) -> green
- 1700 < output_power <= 2600 W (approx 50-80% of rated capacity) -> amber
- output_power > 2600 W (above 80% of rated capacity) -> red

Severity mappings:
  "unknown":  grey text, no badge, or "N/A"
  "green":    green text/background (Bulma .has-text-success or .tag.is-success)
  "amber":    amber text/background (Bulma .has-text-warning or .tag.is-warning)
  "red":      red text/background (Bulma .has-text-danger or .tag.is-danger)

The severity class is applied only to the output power value element.
No other metric receives severity colouring in this PR.

TIMESTAMP CONTRACT

CANONICAL FIELD: inverter[0].observed_at (already exists on InverterReadSnapshot).

SOURCE: DeviceData.timestamp.  Currently a naive local-time string
("%Y-%m-%d %H:%M:%S") created by time.localtime() in the DESS API fallback path,
or an API-provided string from the primary path.  The server running
dessmonitor is in Europe/London timezone.

NORMALIZATION STRATEGY (decision — implement exactly one):

Option A (preferred — JS-side normalization):
  Assume the naive timestamp string "YYYY-MM-DD HH:MM:SS" represents
  Europe/London local time.  Convert in JS by appending a timezone suffix
  before parsing:
    new Date(isoString + " GMT+0100") during BST (April-October)
    new Date(isoString + " GMT+0000") during GMT (October-March)
  However, this requires DST auto-detection in JS.

Option B (backend emits ISO 8601 with offset):
  Modify _inverter_provider() to emit observed_at as an ISO 8601 string
  with Europe/London offset.  E.g. using Python's datetime with pytz or
  zoneinfo (stdlib in Python 3.9+) to convert the naive local time to
  an aware datetime, then format as "2026-07-25T12:00:00+01:00".
  This is the cleanest approach — JavaScript Date parser handles ISO 8601
  consistently.

Option B selected.  The _inverter_provider() lambda in run.py will:
  1. Read dd.timestamp (naive str "%Y-%m-%d %H:%M:%S" or None).
  2. Determine whether the string has a timezone marker.  If already
     ISO-like (contains "T" or "Z" or offset), pass as-is.
  3. If naive, assume Europe/London local time:
     - Use zoneinfo.ZoneInfo("Europe/London") to localize the naive time.
     - Convert to UTC-aware ISO 8601 with offset.
  4. Emit as "observed_at" in the inverter dict.

This requires adding `from zoneinfo import ZoneInfo` to run.py (stdlib
since Python 3.9).  No external dependency.

FRESHNESS CONTRACT

Freshness is computed client-side in dashboard.js from inverter.observed_at.

The inverter poll interval is 60s.  Dashboard poll interval is 5s.  Freshness
thresholds based on time since inverter-reported timestamp:

- observed_at is null or undefined -> freshness = "unavailable"
  Visual: grey badge "unavailable", no colour.
- Current time - observed_at <= 150 seconds (2.5x poll interval)
  -> freshness = "fresh"
  Visual: green badge "fresh" (same pattern as sensor freshness).
- Current time - observed_at <= 600 seconds (10x poll interval)
  -> freshness = "stale"
  Visual: amber badge "stale" (same pattern as sensor freshness).
- Current time - observed_at > 600 seconds
  -> freshness = "unavailable"
  Visual: grey badge "unavailable" (same pattern as sensor freshness).

This is consistent with the existing sensor freshness rendering pattern
(fresh/stale/unavailable badges in the Sensors table).

RISKS
1. Timezone conversion in run.py adds a zoneinfo import (stdlib, no
   external dependency).  Risk: zoneinfo may not have Europe/London data
   on minimal Docker images.  Mitigation: the Debian/Ubuntu-based Docker
   image for Python 3.12+ includes tzdata by default.  Document as a
   runtime dependency in the run.py comment.

2. The primary API path for timestamp (_parse_device_data) passes the
   string directly from the API.  If the API returns a timezone-aware
   string, the naive-time assumption could produce double-conversion.
   Mitigation: _inverter_provider() already checks for "T" or "Z" or
   offset patterns.  If the string already contains timezone info, pass
   as-is.  Only naive "YYYY-MM-DD HH:MM:SS" format triggers conversion.

3. Severe weather or extremely high load could trigger red severity
   persistently.  This is correct behaviour — the operator should see
   red when the inverter is above 80% of rated capacity.  No threshold
   hiding.

4. Freshness threshold (150s for fresh, 600s for stale) assumes 60s
   inverter poll interval.  If the interval changes, the thresholds
   must be reviewed.  Document this dependency in the code.

5. Existing check-compact-operator-dashboard.sh tests verify element
   presence by ID.  New IDs must not collide with existing ones.

  alongside the source indicator.  A full inverter timestamp label
  goes in the inverter detail section below sensors.

- Should the freshness badge reuse the sensor freshness CSS classes
  (tag is-success, is-warning, is-light) or have dedicated classes?
  Decision: Reuse the same tag pattern for consistency.  The classes
  `tag is-success is-light` / `tag is-warning is-light` / `tag is-light`
  are already defined by Bulma and used by sensor freshness.

- Should inverter freshness update inside the render cycle or have
  its own timer?  Decision: Compute freshness during each render cycle
  (every 5s poll).  No separate timer — the existing poll cycle
  provides sufficient granularity for freshness states (fresh >= 150s,
  stale 150-600s, unavailable > 600s).  A 5-second granularity is
  adequate for multi-minute thresholds.

WEATHER AND PREDICTION DEFERRAL
Weather forecast was requested as a separate feature.  It is not part
of this PR scope.  Weather requires a new backend data source (OpenWeather
API), a typed weather contract, and potentially a new inverter-neutral
section in the dashboard.  It should be planned as a separate PR with
its own data-source ingestion and typed projection work.

Prediction (next-hour PV, load forecasting) is an ML feature that
requires the TimescaleDB history pipeline and ML advisory integration.
It is deferred beyond the current observability-focused sequence.
